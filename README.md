# E-commerce Business Analytics — PostgreSQL, SQL & Python

An end-to-end e-commerce analytics project built to demonstrate practical analyst skills across data modeling, SQL analysis, Python validation, data quality, profitability analysis, customer analytics, and client-style reporting.

The project uses a reproducible synthetic transactional dataset covering the 2025 calendar year and follows a complete analyst workflow:

```text
Data Generation
      ↓
PostgreSQL Database
      ↓
Data Quality Validation
      ↓
SQL Business Analysis
      ↓
Python Analysis
      ↓
SQL vs Python Cross-Validation
      ↓
Business Findings
      ↓
Dashboard / Client Reporting
```

> **Note:** The dataset is synthetic and is intended for learning, portfolio demonstration, and interview preparation. The reported business values should not be interpreted as real company performance.

---

## 1. Project Objective

The goal is to turn relational e-commerce transaction data into business insights that answer questions such as:

- How much realized revenue did the business generate?
- How is revenue changing over time?
- Which customers contribute the most value?
- How many customers are repeat buyers?
- Which products and categories drive revenue and profit?
- Where are returns reducing realized value?
- Which regions produce the strongest contribution profit?
- Which customers appear to be at risk of inactivity?
- Which acquisition channels and campaigns show the strongest descriptive performance?
- What actions should management investigate next?

The project emphasizes **analytical correctness**, not only SQL syntax. Table grain, metric definitions, joins, data quality, independent validation, and business interpretation are treated as part of the analytical workflow.

## 3. Data Model

The main transactional relationship is:

```text
customers
    │
    │ customer_id
    ▼
orders
    │
    │ order_id
    ▼
order_items
    │
    │ product_id
    ▼
products
```

Additional relationships:

```text
orders.campaign_id
        │
        ▼
campaigns.campaign_id

returns.order_id
        │
        ▼
orders.order_id

returns.order_item_id
        │
        ▼
order_items.order_item_id
```

### Why grain matters

`orders` is at **order grain**, while `order_items` is at **order-line grain**.

An order containing four items produces four rows after an order-to-item join.

Therefore:

```sql
COUNT(*)
```

after joining `orders` and `order_items` counts order-item rows, not orders.

For an order-level count:

```sql
COUNT(DISTINCT order_id)
```

is required.

This principle is especially important for AOV, revenue, shipping costs, refunds, and other metrics.

The PostgreSQL schema defines primary keys, foreign keys, checks, and supporting indexes. See [`sql/01_schema.sql`](sql/01_schema.sql).

## 6. Analytical Methodology

The analysis follows a grain-aware workflow:

```text
Raw transaction tables
        ↓
Line-level calculations
        ↓
Order-level aggregation
        ↓
Customer / Product / Region / Month analysis
        ↓
Business interpretation
```

This structure reduces the risk of row multiplication and double-counting.

### Realized-sales rule

Only orders with:

```text
status = 'Delivered'
```

are included in realized-sales analysis.

## 7. Metric Definitions

### Gross Sales

```text
Gross Sales = quantity × unit_price
```

### Discount

```text
Discount = quantity × unit_price × discount_pct
```

### Net Sales Before Returns

```text
Net Sales Before Returns = Gross Sales − Discount
```

### Refunds

```text
Refunds = sum(refund_amount)
```

### Net Revenue

```text
Net Revenue = Net Sales Before Returns − Refunds
```

### COGS

```text
COGS = quantity × unit_cost
```

### Contribution Profit

```text
Contribution Profit
= Net Revenue − COGS − Shipping Cost
```

### Contribution Margin

```text
Contribution Margin %
= Contribution Profit / Net Revenue × 100
```

### AOV

```text
AOV = Net Revenue / Delivered Orders
```

These definitions are analytical assumptions for this synthetic project. In a real client engagement, Finance/Analytics definitions should be confirmed before reporting.

See [`docs/methodology_and_metrics.md`](docs/methodology_and_metrics.md).

## 15. Key Business Insights

The current verified analysis supports several high-level observations:

### Strong Q4 performance

October, November, and December are materially stronger than most earlier months, with December the highest month in the verified revenue series.

### Discounts and refunds are material

Gross sales are substantially higher than realized net revenue because discounts and refunds reduce the final realized value.

### Revenue should not be viewed alone

The project intentionally evaluates customer retention, returns, product margin, and contribution profitability alongside revenue.

### Campaign results require caution

Campaign-attributed revenue is descriptive. High revenue associated with a campaign does not by itself prove incremental campaign impact or ROI.

See [`docs/business_findings.md`](docs/business_findings.md) for the detailed interpretation and recommendation framework.

## 16. Business Recommendations

The analysis framework supports the following actions:

1. **Improve repeat purchasing** by identifying one-time buyers and high-value customers becoming inactive.
2. **Prioritize profitable growth** by evaluating contribution profit and margin alongside revenue.
3. **Investigate high-return products** using both return rate and return reasons.
4. **Decompose Q4 growth** into order volume, AOV, customer mix, category mix, and campaign activity before increasing investment.
5. **Treat campaign analysis as descriptive evidence** until incremental measurement or experimentation is available.

Recommendations should be updated when the final customer, product, returns, and profitability outputs are refreshed.

## 19. Historical Analysis Rule

The dataset ends on:

```text
2025-12-31
```

Historical churn/inactivity calculations should therefore use:

```sql
DATE '2025-12-31'
```

rather than:

```sql
CURRENT_DATE
```

Otherwise, the same historical analysis would change as real-world time moves forward.

## 20. Analytical Limitations

This is a synthetic portfolio project, so the following limitations apply:

- The dataset does not represent a real company's performance.
- Cost and shipping values are generated assumptions.
- Customer segment thresholds are project-defined.
- The 90-day churn threshold is a project-defined proxy.
- Campaign performance is descriptive rather than causal.
- True campaign ROI would require incremental measurement, attribution, or controlled experimentation.
- Revenue recognition and refund timing are simplified for analytical purposes.

## 23. Project Takeaway

The main lesson from this project is that analytical correctness depends on more than writing a syntactically valid query.

A reliable analyst workflow is:

```text
Understand the data
      ↓
Validate the data
      ↓
Define the metric
      ↓
Respect table grain
      ↓
Calculate at the correct level
      ↓
Cross-check the result
      ↓
Interpret the finding
      ↓
Recommend a measurable action
```

The project therefore demonstrates an end-to-end analyst workflow rather than a collection of isolated SQL exercises.
